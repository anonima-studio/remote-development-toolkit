# Local agents, remote execution

> Перевод. Источник: [docs/methodology.md](../methodology.md). При расхождении
> верен английский текст.

Это методология, которую реализует набор. Каждый принцип записан как
**Проблема → Правило → Чем обеспечено**. «Обеспечено» всегда указывает на код
или тест в этом репозитории: принцип без такой точки был бы просто советом.

## 1. Агенты — нагрузка, а не control plane

**Проблема.** Агент, который может создавать серверы, править правила
файрвола или решать, на каком хосте выполнить команду, превращает каждый
промпт в изменение инфраструктуры. Его ошибки трудно проверить и откатить.

**Правило.** Инфраструктурные решения принимают детерминированные программы и
декларативное состояние. Агенты правят исходники и запускают команды проекта
внутри границы, которую программа уже выбрала и проверила.

**Чем обеспечено.**

- Базовая настройка хоста, развёртывание, импорт шаблона и расписание —
  shell-программы: [`bootstrap/ubuntu.sh`](../../bootstrap/ubuntu.sh),
  [`deploy/install.sh`](../../deploy/install.sh),
  [`templates/docker/main.tf`](../../templates/docker/main.tf).
- В режиме `local-agent` агент получает семь инструментов runner, в схемах
  которых нет полей хоста, workspace, профиля или пути. Маршрут берётся из
  доверенного контекста запуска:
  [`bin/remote-dev-local-agent-mcp.mjs`](../../bin/remote-dev-local-agent-mcp.mjs),
  тест [`tests/remote-dev-local-agent-mcp-smoke.sh`](../../tests/remote-dev-local-agent-mcp-smoke.sh).
- Workspace никогда не получают Docker-сокет хоста; он есть только у
  provisioner Coder ([`deploy/coder/compose.yaml`](../../deploy/coder/compose.yaml)).

## 2. Результат засчитывается, только когда пользователь его видит

**Проблема.** «Сервер запущен на `localhost:3000`» верно внутри удалённого
контейнера и бесполезно на Mac оператора. Инфраструктуру, тесты и настройки
легко объявить готовыми, когда открыть результат никто не может.

**Правило.** Каждый пользовательский сценарий называет четыре вещи: точку
входа (команда, URL, файл или элемент интерфейса), точное действие, видимый
результат и путь восстановления, если результата нет. `localhost` внутри
workspace — не результат.

**Чем обеспечено.**

- `remote-dev preview` печатает `READY` только после HTTP-ответа через открытый
  им туннель и печатает URL для Mac ([`bin/remote-dev`](../../bin/remote-dev),
  `run_workspace_preview`; [`tests/remote-dev-preview-smoke.sh`](../../tests/remote-dev-preview-smoke.sh)).
- `project-setup` ждёт настоящий 2xx от объявленного health URL проекта и
  затем печатает точки входа на Mac
  ([`tests/remote-dev-project-setup-smoke.sh`](../../tests/remote-dev-project-setup-smoke.sh)).
- `codex-desktop` сообщает `READY` только после того, как дошёл до удалённого
  Codex через созданный им SSH-алиас
  ([`tests/remote-dev-codex-desktop-smoke.sh`](../../tests/remote-dev-codex-desktop-smoke.sh)).
- Каждая ошибка этих команд печатает одно конкретное действие для
  восстановления; в руководствах есть таблица восстановления для каждого
  сценария.
- Правило входит в контракт агентов [`AGENTS.md`](../../AGENTS.md) и skill
  [`remote-development`](../../.agents/skills/remote-development/SKILL.md).

## 3. Идентичность развёртывания закрывается при отказе

**Проблема.** SSH-алиас — ещё не развёртывание. Правильная команда,
направленная на чужой сервер, или недописанный профиль, направленный на
настоящий, незаметно смешивают состояние двух развёртываний.

**Правило.** Каждая команда называет своё развёртывание. Идентичность
развёртывания — полный, проверенный, несекретный файл профиля. Неполная или
противоречивая идентичность останавливает операцию до первого изменения на
сервере.

**Чем обеспечено.**

- Профиля по умолчанию нет: [`deploy/host-profiles/load.sh`](../../deploy/host-profiles/load.sh)
  отказывается работать без `--profile` или `REMOTE_DEV_PROFILE`, запрещает
  подменять записанную идентичность через `REMOTE_DEV_HOST` и проверяет каждое
  поле для выбранной топологии.
- Первое удалённое действие `install` — проверка идентичности только на
  чтение.
- Операции с секретами и паролями требуют повторного подтверждения workspace,
  профиля и origin Coder (`--confirm`, `--confirm-profile`, `--confirm-origin`).
- [`tests/remote-dev-cli-smoke.sh`](../../tests/remote-dev-cli-smoke.sh)
  гоняет CLI только на синтетических профилях и проверяет отказы.

## 4. Жизненный цикл явный; после неизвестного исхода — сверка, а не повтор

**Проблема.** Оборванное SSH-соединение не говорит, закончилась ли сборка,
создание workspace или удалённая команда. Слепой повтор может дважды выполнить
миграцию или создать второй workspace. Скрытый автозапуск превращает проверку
статуса в решение о ресурсах.

**Правило.** Операции чтения никогда не запускают workspace. После
неизвестного исхода следующий шаг — прочитать записанное состояние и
сверить его, а не отправить запрос заново. Каждое многошаговое изменение
сначала пишет журнал или квитанцию и продолжается с них.

**Чем обеспечено.**

- Статус, exec, preview, секреты и SSH для Codex Desktop работают с Coder при
  выключенном автозапуске; остановленный runner возвращает `WORKSPACE_STOPPED`,
  и запускает его только явный инструмент `runner_resume` или
  `local-agent resume`.
- Local Agent записывает неизвестный исход выполнения и блокирует дальнейшую
  работу, пока явно не выбран `--recover-unknown`
  ([`tests/remote-dev-local-agent-recovery-gate-test.sh`](../../tests/remote-dev-local-agent-recovery-gate-test.sh),
  [`tests/remote-dev-local-agent-smoke.sh`](../../tests/remote-dev-local-agent-smoke.sh)).
- Переключение режимов ведёт устойчивый журнал; `mode resume` повторяет ту же
  операцию, а запрос на создание workspace с неизвестным исходом никогда не
  отправляется повторно ([`tests/remote-dev-mode-operation-test.py`](../../tests/remote-dev-mode-operation-test.py),
  [`tests/remote-dev-workspace-plan-test.py`](../../tests/remote-dev-workspace-plan-test.py)).
- `codex-update` и `pids-rollout` пишут квитанции на хосте; существующая
  квитанция блокирует второе изменение
  ([`tests/remote-dev-codex-update-test.py`](../../tests/remote-dev-codex-update-test.py)).

## 5. Один источник истины на рабочую копию, одна роль на workspace

**Проблема.** Две записываемые копии одних исходников, синхронизируемые в обе
стороны, рано или поздно расходятся, и уже нельзя сказать, с какой из них
получен результат теста.

**Правило.** У каждой рабочей копии ровно одно авторитетное место: Git
checkout в workspace разработки (`remote`) или Git-корень либо working set на
Mac (`local-agent`). Передача односторонняя. Роль workspace не меняется за всю
его жизнь; смена роли — это новый workspace.

**Чем обеспечено.**

- Шаблон пишет неизменяемый маркер роли; управляемые точки входа отказывают
  при несовпадении ([`templates/docker/workspace-role.sh`](../../templates/docker/workspace-role.sh),
  [`tests/remote-dev-workspace-role-smoke.sh`](../../tests/remote-dev-workspace-role-smoke.sh)).
- Runner получает проекцию без `.git`. Любое изменение управляемых исходников
  на runner становится `REMOTE_DRIFT`, приостанавливает синхронизацию и
  блокирует следующую команду до явного выбора восстановления. Runner занят
  одной привязкой; вложенный worktree внутри привязанного корня получает
  `NESTED_WORKTREE_UNBOUND`, а не чужой runner
  ([`tests/remote-dev-local-agent-smoke.sh`](../../tests/remote-dev-local-agent-smoke.sh)).
- Каждая команда на runner оставляет квитанцию с манифестом исходников, на
  которых она выполнялась.
- Переключение режимов переносит авторитетность через «заборы» и публикацию
  сначала в неактивном виде; наличие файлов по пути никогда не считается
  авторитетностью ([`tests/remote-dev-mode-guard-test.py`](../../tests/remote-dev-mode-guard-test.py),
  [`tests/remote-dev-mode-endpoint-test.py`](../../tests/remote-dev-mode-endpoint-test.py)).

## 6. Никакого собственного control plane: Coder плюс узкие адаптеры

**Проблема.** Инструменты удалённой разработки обрастают своим
планировщиком, реестром, API и панелью, и каждому нужна своя модель
безопасности, резервное копирование и обновления.

**Правило.** Пользователями, шаблонами, жизненным циклом workspace и связью с
агентами владеет Coder. Набор добавляет тонкие проверяемые адаптеры вокруг
него и не вводит своего демона, реестра или базы данных.

**Чем обеспечено.**

- `workspace create` — обёртка над `coder create`, которая задаёт параметры
  шаблона и проверяет маркер роли ([`bin/remote-dev-workspace`](../../bin/remote-dev-workspace)).
- На хост ставятся только Compose-проект Coder, oneshot-юнит сетей и
  необязательные юниты `cloudflared` и резервного копирования
  ([`deploy/`](../../deploy), [`backup/`](../../backup)).
- `status` и `audit` только читают Coder, Docker и хост и ничего не удаляют.

## 7. Секреты перемещаются только по проверенным манифестам

**Проблема.** Секреты утекают через аргументы команд (видны в `ps`), историю
shell, логи, квитанции, Git и «временные» копии.

**Правило.** Секретный файл перемещается только по маршруту из проверенного
несекретного манифеста, через stdin, в файл с правами `0600`, и проверяется без
вывода значения или хеша. Ничто из записываемого набором не содержит значений
секретов или аргументов команд.

**Чем обеспечено.**

- [`bin/remote-dev-secrets`](../../bin/remote-dev-secrets): `plan` ничего не
  передаёт; `apply` требует точных подтверждений, по умолчанию не заменяет
  существующие файлы, пишет атомарно и проверяет без вывода значений
  ([`tests/remote-dev-secret-upload-test.py`](../../tests/remote-dev-secret-upload-test.py),
  [`tests/remote-dev-secret-read-test.py`](../../tests/remote-dev-secret-read-test.py),
  [`tests/remote-dev-secrets-binding-test.py`](../../tests/remote-dev-secrets-binding-test.py)).
- Пароль владельца показывается один раз через страницу на loopback, которая
  получает его через stdin ([`bin/remote-dev-credential-helper.py`](../../bin/remote-dev-credential-helper.py),
  [`tests/remote-dev-credentials-smoke.sh`](../../tests/remote-dev-credentials-smoke.sh)).
- Квитанции выполнения на runner хранят число аргументов и имя программы, но не
  сами аргументы ([`bin/remote-dev-local-agent`](../../bin/remote-dev-local-agent),
  `write_exec_receipt`).
- Секретные файлы исключены из проекции и из Git
  ([`.gitignore`](../../.gitignore)); CI сканирует каждый push на секреты.

## 8. Возможности агента оператора остаются там, где настроены

**Проблема.** Перенос агента в удалённый workspace незаметно теряет skills,
MCP-серверы, плагины, учётные данные и доступ к браузеру, настроенные на Mac,
или толкает к их копированию на сервер.

**Правило.** Если проект зависит от локальных возможностей агента, агент
остаётся на Mac (`local-agent`), а переносится только нагрузка. Интеграция
добавляет одну запись с собственным именем в конфигурацию агента и больше
ничего не трогает.

**Чем обеспечено.**

- `local-agent install` добавляет одну MCP-запись `remote_dev_local_agent` и
  сохраняет все остальные; `uninstall` удаляет только её и отказывает, пока
  есть активная привязка ([`bin/remote-dev-local-agent-config.mjs`](../../bin/remote-dev-local-agent-config.mjs),
  [`tests/remote-dev-local-agent-config-smoke.sh`](../../tests/remote-dev-local-agent-config-smoke.sh)).
- Инструкции MCP-сервера направляют чтение и правку исходников, Git, skills и
  настройки к локальным инструментам, а зависимости, сборку, тесты, запуск,
  отладку и Docker — к инструментам runner.
- Набор не утверждает, что запрещает нагрузку в локальном shell агента: он
  формулирует правило маршрутизации и доказывает удалённое выполнение
  квитанциями. См. [Limitations](../limitations.md).
